# Архитектурные решения и рефлексия

## ✅ Принятые решения

### 1. Стек технологий
Выбран минималистичный стек **FastAPI + PostgreSQL + Chart.js**.
- **FastAPI:** Обеспечивает высокую производительность, автоматическую документацию (Swagger UI) и простую интеграцию с SQLAlchemy.
- **PostgreSQL:** Используется "как есть" из дампа. Мы не меняем схему, а адаптируем запросы под существующую структуру Django-проекта.
- **Chart.js:** Легковесная библиотека для отрисовки графиков прямо в браузере, не требующая сложной сборки фронтенда.

### 2. Безопасность данных (Read-Only)
Так как требование — "данные в базе менять нельзя", защита реализована на двух уровнях:
- **Уровень БД:** В скрипте инициализации создается пользователь `cliniciq2_user` с правами только на `SELECT`.
- **Уровень приложения:** В соединении SQLAlchemy установлен флаг `default_transaction_read_only=on`. Это гарантирует, что даже если разработчик случайно напишет `INSERT` или `UPDATE`, транзакция будет отклонена базой данных.

### 3. Восстановление дампа
Использован механизм `docker-entrypoint-initdb.d`. Скрипт `01-restore.sh` автоматически разворачивает базу из бинарного дампа (`pg_restore`) при первом запуске контейнера. Это делает репозиторий самодостаточным: любой разработчик может поднять копию продакшн-среды одной командой.

### 4. Аналитика на лету
Отчеты формируются прямыми SQL-запросами без использования промежуточных таблиц агрегации. Для текущих объемов данных (~280k приемов) это работает достаточно быстро (<1 сек). Использованы CTE (Common Table Expressions) для сложной логики подсчета перенаправляемости.

## ⚠️ Ограничения текущей реализации

1. **Жесткая привязка к схеме:** Имена таблиц и полей захардкожены в `queries.py`. Если схема БД изменится, отчеты сломаются.
2. **Производительность на больших объемах:** При росте базы до миллионов записей прямые SQL-запросы могут стать медленными. Отсутствие индексов на полях фильтрации (например, `start_time`) может вызывать Full Scan.
3. **Отсутствие кэширования:** Каждый клик по кнопке "Сформировать отчет" вызывает новый тяжелый запрос к БД.

## 🔮 Что бы я сделал иначе при большем времени

1. **Слой материализации (Materialized Views / DBT):**
   Вместо raw SQL на лету я бы внедрил инструмент типа **dbt (data build tool)**. Он позволял бы описывать трансформации данных как код, строить граф зависимостей и создавать материализованные представления. Это ускорило бы отдачу данных до миллисекунд.

2. **Динамическая инспекция схемы:**
   Написать модуль, который при старте сканирует `information_schema`, находит таблицы с ключевыми словами (`appointment`, `transaction`, `user`) и автоматически строит маппинг полей. Это сделало бы решение универсальным для любых медицинских CRM на Django.

3. **Кэширование и асинхронность:**
   Внедрить **Redis** для кэширования результатов запросов на 5–15 минут. Для очень тяжелых отчетов реализовать асинхронную генерацию через Celery с уведомлением пользователя о готовности.

4. **CI/CD и качество кода:**
   Настроить GitHub Actions для автоматического прогона линтеров (black, ruff), типов (mypy) и тестов при каждом пуше. Добавить автоматический деплой на VPS через SSH.

5. **Обработка отрицательных сумм:**
   В текущей реализации выручка может быть отрицательной (возвраты/корректировки). Я бы добавил четкую бизнес-логику фильтрации транзакций по типу операции (`operation_type`) или статусу, чтобы отображать только чистый доход.
